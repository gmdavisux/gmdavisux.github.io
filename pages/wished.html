01 — Origin

In late 2025, I came across a blog post by designer Adrienne Baker: Shaping AI Experiences: A Practical Guide for UX Practitioners Who Want to Design the System, Not Just the Interface. Her argument was that designers should be shaping the system prompt — not just the UI wrapped around it.

I wasn't new to the problem. After nearly 30 years in UX — most recently designing AI-enabled document processing at Xerox, and before that human-in-the-loop image review systems at EagleView — I had lived the frustration of working on AI features where the behavior felt wrong and there was no clear way to change it. The voice was off. The guardrails too rigid. The output didn't match what users needed. And the system prompt lived in a code file, owned by engineering.

"I was familiar with the problem of AI having the wrong voice or behavior and feeling helpless to change it. It was exciting to know I could affect it."

Gary Davis

That recognition sparked a question I couldn't let go of: if the system prompt is fundamentally an interaction design problem, why doesn't a designer-friendly tool for it exist? I decided to build one.

02 — Problem

When product teams integrate AI, the workflow tends to collapse the same way: a PM writes requirements, an engineer writes the system prompt, and the designer is handed a chat window to put a UI around. The behavior — the voice, the guardrails, the response format, the edge case handling — is treated as a technical implementation detail.

But AI behavior is fundamentally a user experience problem. How a system responds to frustration, ambiguity, or an off-topic question shapes user trust more than any visual design decision. The "iceberg" of an AI product — everything beneath the interface — is almost entirely interaction design work.

The Ownership Gap
Designers show up late

Prompt development happens in scattered tools — code repos, shared docs, individual ChatGPT sessions — before designers are involved.

The Tooling Gap
No purpose-built workspace

Existing tools like PromptLayer and LangSmith are built for developer workflows. Nothing is designed for cross-functional UX teams.

The Handoff Gap
No path to engineering

Even when designers shape AI behavior informally, there's no structured way to document decisions or produce a handoff package engineers can work from.

03 — Research

Before building deep, I recruited four participants for working prototype sessions — each representing a different role in the product development process where AI behavior decisions get made.

Steve J.

"Once I do all this and I'm like wow — but now what do I do with it? How do I take this to my product?"

Nimisha D.

"This is so amazing. This is so useful. I'm one of your users."

Evelyn S.

Strategy Consultant · HCI background

"My end goal is not the system prompt — my end goal is the experience and the outcome."

Three themes cut across every session

  • 01
    The "Now What?" problem

    Every participant found value in the design and iteration experience — then hit the same wall. The handoff from behavior design to engineering was completely unresolved. Steve put it plainly: without a clear path out, the tool felt like a cool sandbox, not a productivity tool.

  • 02
    Domain experts configure better AI than engineers

    Steve said it directly: "A PM who knows their users can probably create a better assistant than an engineer who doesn't." All four sessions demonstrated this. The people closest to user needs are best positioned to define AI behavior — validating the tool's core premise.

  • 03
    The blank slate kills momentum

    Three of four participants hesitated at the empty starting state. Kate identified the fix: auto-generate an initial AI greeting on project creation, so the first action is "here's what you have — now improve it" rather than "figure out where to start."

04 — The Design

The tool is built around five interconnected pieces, each designed to match how designers and PMs already think — not how engineers do.

Define purpose and voice first

When creating a project, designers set the AI's name, purpose, interaction type, and voice archetype — options like "Playful Helper," "Trusted Expert," or "Confident Partner." These choices seed the automatically generated system prompt, grounding behavior in UX intent from the start. The AI provider and model are locked at creation, keeping behavior testing consistent and the export targeted at the right platform.

Project Details — voice archetype, interaction type, and AI provider configured at project creation

Natural language refinement — no prompt syntax required

Every response in the live test chat has an Improve button. Clicking it opens a panel where the designer describes what they want changed in plain language — "ask one question at a time," "be warmer," "skip the causes, just give the fix." The system then proposes a specific, labeled change to the system prompt (prepend, modify, or delete) alongside a preview of the improved response.

This was the interaction Evelyn described as fitting "the thinking pattern of someone who's building something" — no prompt syntax, no digging through instructions.

The proposed change is labeled "prepend" — the designer sees exactly what will change and how the response will improve

Designer stays in control at every step

Proposed changes are never applied automatically. The designer reviews the full proposed system prompt update and a predicted response, then explicitly approves or rejects. If the change isn't right, they refine the description and generate a new proposal.

This gate was a direct response to a finding from Kate: without it, users continued typing and accidentally sent improvement requests against the wrong response, breaking the conversation state entirely.

No change is applied until the designer explicitly approves it

The system prompt has a version history

The System Prompt drawer shows the current prompt alongside a version counter (v1 of 2, v2 of 2, etc.). Designers can browse back through every previous version — each tied to the improvement request that generated it.

This creates a built-in design rationale record. For the first time, the behavioral decisions behind an AI feature are documented as naturally as Figma version history documents visual decisions.

System Prompt at v2 of 2 — Role, Tone, Rules, and Constraints shaped iteratively through the Improve flow

Two export formats for archive and handoff

The Export modal is the direct answer to the "Now What?" problem every participant hit. Full Project Backup includes version history, all settings, and a README with restore instructions. Deployment Package strips the history and produces clean prompt files, a runtime configuration JSON, and a deployment guide ready for engineering.

Both exports are model-agnostic — the configuration translates whether the production system runs on Claude, OpenAI, or Gemini.

Full Backup for design archives; Deployment Package for engineering handoff

05 — How I Built It

I built the entire product myself using GitHub Copilot as a coding collaborator — no engineering team. The irony was intentional: I was using AI to build a tool for designing AI. Every friction point I hit as a builder directly informed a design decision in the product.

  • 1
    Layout & component structure

    Built the two-panel workspace shell — left nav with project drawers (Project Details, System Prompt, Greeting Prompt, Advanced Settings, Export), right-side live chat — establishing component patterns before adding functionality.

  • 2
    LLM integration & the Improve interaction

    Connected to multiple AI providers (Anthropic, OpenAI, GroqCloud) with streaming responses. The Improve flow — natural language in, labeled system prompt change out, approve/reject gate — was validated in working code, not just in theory.

  • 3
    Version control for prompts

    Built a versioning system specific to prompt evolution — tracking what changed, when, and what improvement request caused it. Each version is browsable in the System Prompt drawer.

  • 4
    Export & handoff package

    Built the two-path export system — Full Project Backup and Deployment Package — as the direct response to the "Now What?" finding that surfaced in every research session.

  • 5
    Research sessions & iteration

    Ran four working prototype sessions, synthesized findings into an 18-item prioritized backlog, and shipped improvements directly in response to what I observed. The live product today reflects those findings.

06 — Outcomes

Every participant independently confirmed that the gap this tool addresses is real and currently unserved. The research produced a ranked backlog shaping what gets built next: auto-generated greetings (P0), scenario testing (P1), team collaboration features (P2).

07 — Reflection

This project tested a different kind of UX capability. I wasn't embedded in a product team — I was the whole team. That constraint produced some of the clearest design thinking I've done in years.

What worked
  • Starting with "the system prompt is a design artifact" kept every decision anchored to users throughout
  • Running research on a working prototype generated far richer feedback than any mockup would have
  • Building it myself gave genuine empathy for the exact users I was designing for
  • The Improve interaction solved a hard problem: natural language intent, structured output, designer in control at every step
What I'd do differently
  • The "vs custom ChatGPT" differentiation needed an answer baked into onboarding — two participants asked it and the UI had nothing ready
  • The auto-generated greeting should have been in v1 — the blank chat state cost participants momentum in every single session
  • API key onboarding is still too technical for the non-developer designer persona
  • Scenario testing belongs in the core loop — two participants described it independently without prompting

"Models are becoming fairly commoditized. What's actually more impactful to whether a user gets value is how it gets harnessed."

Steve J., PM · Beta participant

Steve's observation is why this project matters to me. The design layer — the behavior, the voice, the guardrails — is where user value is actually created or destroyed. That layer belongs to designers. AI·UX Behavior Studio is my attempt to give them a place to do that work.
